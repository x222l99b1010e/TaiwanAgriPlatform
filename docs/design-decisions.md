4. 免費額度的算術，讓同步程式不能常駐（§4.1）
5. 被推翻的判斷：當時怎麼想、怎麼發現、改了什麼（§7）

## 1 專案一覽

### 1.1 做什麼

農業部開放資料平台（data.moa.gov.tw）上的氣象、行情、農藥、食品追溯、寵物等資料，分散在各自的 API 與網頁。這個平台定期把它們同步進同一個資料庫，整理成四個模組：

| 模組 | 對象 | 內容 |
|---|---|---|
| 1 生鮮物價與食安透明網 | 消費者 | 今日菜價、農產品追溯、農藥違規名單、有機驗證查詢 |
| 2 智慧青農戰情室 | 農民 | 農場氣象、雨量趨勢、病蟲害警報與旬報、農藥查詢、自訂通知規則 |
| 3 毛小孩守護地圖 | 飼主 | 收容動物地圖、官方與使用者的遺失協尋、合法寵物業者查詢 |
| 4 大數據探險 | 研究者 | 農產品、毛豬、家禽行情，天災事件與菜價疊圖，休市日 |

另外有註冊登入（JWT）、依角色顯示的導覽列、農場偏好設定與監看清單。

開發照週次排程（W1–W26，文中的 W19、W26 指的是這個編號）；code review、視覺設計、部署、容器化這類不屬於某個週次的工作，不掛週次。

### 1.2 規模

以下是 2026-10-20 `main`（[`241915d`][c-241915d]）的數字：

| 項目 | 數量 |
|---|---|
| 開發期間 | 2026-04-06 第一個 commit 到 2026-10-20，197 天；`main` 上 314 個非 merge commit |
| 後端 | C# 342 個檔、約 34,900 行；9 個 .NET 專案（含測試）；API 端點 46 支（另有 2 支健康檢查） |

| 背景同步 | 17 支排程程式（16 支資料同步＋1 支通知規則引擎），串接農業部 26 個 API 端點（含 2 支舊制端點） |
| 前端 | Vue 3，59 個 `.vue` 檔、34 條路由 |
| 測試與 CI | 後端 488 則、前端 169 則；CI 三個 job（後端、前端、容器映像建置） |

### 1.3 架構

```
          data.moa.gov.tw  (MOA open data APIs)
                    |
                    v
   +--------------------------------+      GitHub Actions
   | TaiwanAgri.Worker              | <--- daily, run once
   | 17 scheduled workers           |
   +---------------+----------------+
                   | EF Core (7 DbContexts)
                   v
   +--------------------------------+
   | SQL Server  /  Azure SQL       |
   +---------------+----------------+
                   ^
                   | EF Core
   +---------------+----------------+      +----------------------+
   | TaiwanAgri.Web  (Web API)      | <--- | Vue 3 frontend       |
   | ASP.NET Core, JWT, 46 APIs     | HTTPS| (Cloudflare Pages)   |
   +--------------------------------+      +----------------------+
```

- **資料流是單向的**：同步程式（Worker）從農業部抓資料、寫進資料庫；Web API 只從資料庫查，不在使用者的請求裡打農業部（農藥查詢與農產品追溯兩項例外：查一次就走、不需要歷史，直接轉查農業部）。
- **模組化單體**：一個方案、一個資料庫，但每個模組是獨立的專案，各自有自己的 DbContext（EF Core 裡對應一組資料表的單位）；氣象、行情、食安、寵物四個模組的資料表另外分在各自的 schema（資料庫裡的命名空間，例如 `market.PoultryTrans`）。跨模組的關聯一律用「邏輯外鍵」——欄位存對方的 ID，但資料庫不建約束（§3.1）。
- **Redis 快取與 RabbitMQ 訊息佇列是可選的**：沒設定就走降級路徑，服務照常啟動。部署時因此只需要資料庫、後端、前端三個服務（§4.2）。

部署形態（2026-10-12 上線）：資料庫是 Azure SQL 免費方案（閒置約 16 分鐘自動暫停）、後端是 Azure App Service 免費層、前端是 Cloudflare Pages、每日同步由 GitHub Actions 觸發。本機則可以用 `docker compose --profile app up` 一條指令起整站（§5）。

## 2 外部資料的形狀決定設計

這個專案多數的設計難題不在框架，而在外部資料：API 文件寫的、規劃時假設的，跟實際回傳的常常不一樣。

### 2.1 接新資料源，第一天先打 API

從 2026-08 的農藥查詢起，接新的資料源一律先花一天實際呼叫 API、看真實資料，再定設計，不照原規劃直接動工。農藥查詢（§2.3）與家禽行情（§2.2）兩輪都因此推翻了原規劃。這一章其餘幾則，則是在探勘、驗收或上線之後才看清的資料形狀。

### 2.2 家禽報價有 14.1% 不是數字：先窮舉，再決定要幾種狀態（[#30][pr30]）

家禽行情來自農業部四支 API，價格欄位是字串。開工規劃只預期「空字串 → null」，第一次實測就出現中文的「休市」。無法確定還有多少沒見過的寫法，於是窮舉全歷史：四支來源、20,614 天、攤平後 88,236 個價格儲存格。

| 原始值 | 次數 | 意思 |
|---|---:|---|
| `""` | 5,426 | 該欄當期不提供 |
| `休市` | 3,585 | 當天沒有交易 |
| `-` | 3,353 | 有交易但沒報價 |
| `41-42` 等 | 70 | 區間報價 |
| `議價` | 7 | 買賣雙方議定 |
| `31..8` | 1 | 鍵入錯誤 |

合計 12,442 格、佔 14.1% 不是數字；紅羽土雞南區兩條線超過三分之一的天數沒有數值，雞蛋產地價 94% 沒有。照「轉不成數字就存 null」，這 14% 會全部變成同一種「沒有資料」，畫面分不出「這個指標本來就少報價」和「同步壞了」。

- **設計**：`Price`（可為 null）＋ `PriceStatus`（7 種狀態）＋ `RawValue`（原文）。
- **狀態要幾種，是資料回答的問題**：初版只有正常、空白、休市、無法辨識四種。照初版做，「無法辨識」會裝進 3,431 筆，失去示警的作用——一個狀態什麼都裝，就什麼都沒說。定版擴成七種，「無法辨識」在全歷史只剩 1 筆（就是那筆 `31..8`）。
- **區間報價不取中間值**：把 `41-42` 存成 41.5，等於發明一個來源從沒說過的數字。原文留在 `RawValue`。
- **驗收看分布，不只看總數**：回填 88,236 列，七種狀態的筆數與探勘時的預估逐一相同。總數相同是最弱的檢查——反序列化時欄位名稱打錯一個字，那一欄會全部變成「空白」，總數不變，分布卻立刻對不上。

同一輪的資料表也由來源形狀決定。四支來源的欄位數分別是 5、6、2、4，互不相同；做成一般的「一個指標一欄」寬表要開 17 個可為 null 的欄位，接第五支來源還得改結構。改成長表（日期、指標代碼、價格三欄固定），「有哪些指標」從結構問題變成資料問題。毛豬行情那張 36 欄的寬表沒有跟著改：它只有一支來源、欄位固定，一致性本身不足以構成重寫的理由。四支來源的歷史起點也不同（2010-10-07 與 2014-04-01），所以各用一組獨立的同步進度，不共用。

### 2.3 農藥查詢：開工第一天的探勘推翻了三支 API 的規劃（[#26][pr26]）

原規劃串接三支 API。第一天實測的結果：

- `PesticideType` 沒有任何可用的查詢參數（試過 13 種參數名都無效，永遠回整張表的前 500 筆），而且它的 5 個欄位在主檔裡全都有 → 排除。
- `PesticideManualType` 停在 2014 年以前：2014 年禁用的達馬松，有 10 個商品在這裡仍列為現行 → 排除。
- 驗收要求的「適用作物、病蟲害」不在三支的任何一支裡，而是在主檔 `ScopeOfUse` 欄位指向的第二層網址——網址結尾是 `.aspx`，看起來像網頁，回傳的卻是 JSON。

定案是一支主檔，加上一個不在規劃內的第二層來源。探勘還量出幾件決定介面的事實：

- **使用範圍掛在「成分＋含量＋劑型」，不是掛在許可證上**：撲殺熱 28 張許可證，背後只有 3 種不同的使用範圍。所以先去重再抓第二層，一般查詢只要個位數次呼叫、1 秒內完成，不必做成延後載入。
- **「未廢止」不等於「有效」**：亞滅培 69 張未廢止的許可證裡，8 張已經過期。兩者分成兩個獨立欄位，畫面上也可能同時成立。
- **截斷要明說**：上游一頁 500 筆、不帶金鑰拿不到第二頁、也沒有總筆數，`Next=true` 是唯一的截斷訊號；截斷後拿到的是依許可證號排序的前 500 筆，跟關鍵字的相關性無關。偵測到就回 400、請使用者縮小關鍵字，不回傳殘缺的結果。
- **對照表要實測校正**：劑型代碼表初版有 17 個代碼照國際標準表直譯。掃過 5,246 張許可證實際出現的 29 種代碼之後，推翻 3 個錯誤譯名、補回 1 個漏收的代碼（實際出現 41 次）、刪掉 8 個從沒出現過的。查不到中文名稱就顯示原始代碼——不好看，但比顯示錯誤的譯名好。

### 2.4 有機驗證：同一個欄位裡的頓號有兩種意思（[#8][pr8]）

有機驗證資料的證書序號欄位，有時是好幾個序號用頓號串在一起。抽樣六十多筆真實資料反推，第一個假設（「一個經營者有幾種驗證行為就有幾張證書」）被下一批資料推翻，最後確認頓號有兩種意思：

- **同一個序號重複兩次**（`1-008-205501、1-008-205501`）：髒資料，清成一個值。
- **不同的序號並列**（`1-009-110011、1-009-120840`）：一筆紀錄合併了同一個經營者的多張證書，要拆成多筆。

拆開之後，同一筆的產品品項欄位仍是未拆的原始字串，無法保證跟拆出來的每張證書精確對應，所以另加一個欄位標記「這筆來自多證書拆分」，在畫面上以徽章揭露，而不是假裝對應得上。

### 2.5 寵物資料：會不會變、平行請求被排隊、每月 1 號的偏態（[#18][pr18]）

**落地策略看「來源資料會不會變」。** 收容動物與官方遺失啟事登記後內容不再變動，只新增、遇到已存在的就略過；合法寵物業者的評鑑等級與營業狀態會隨時間改變，要「新增或更新」。如果業者也用只新增的寫法，評等變了但外部 ID 沒變，整筆會被當成重複丟掉，記錄還寫著「略過 1 筆重複」——看起來一切正常，資料卻悄悄過期。

**只新增的資料，修好轉換邏輯不會讓已存進去的資料變好。** 收容動物的性別欄位出現 API 文件沒寫的 `N`，原本被歸成「其他」。修好對照之後，還得處理已經寫進去的那些：先從同步記錄確認那段期間唯一的未預期值就是 `N`，才能確定所有「其他」都是誤分類，用一句 SQL 補正 97 列。

**平行請求被伺服器排隊。** 官方遺失啟事單次呼叫要 28–35 秒，3,131 天依序抓要 26 小時。用 curl 驗證過「平行有效」之後改成分批平行，實跑卻出現等差的回應時間（22.9、57.6、92.5 秒）——看起來同時送出，實際被伺服器一個一個處理。原因是農業部站台每次回應都設一個 ASP.NET 工作階段 cookie，共用的 `HttpClient` 會記住它，所有請求於是帶著同一個工作階段，而伺服器對同一工作階段的請求會上鎖、依序處理。關掉 cookie 之後，3 個平行請求共 28 秒（共用工作階段時 91 秒）。curl 每次都是新的行程、不共用 cookie，所以測不出這件事：**測平行效果，要用上線時同一份 `HttpClient` 設定**（[`f1b8d82`][c-f1b8d82]）。

**每月 1 號的偏態。** 官方遺失啟事回填完成後逐日統計，每月 1 號的筆數一直明顯偏高，越早期越誇張（2018-09-01 有 350 筆，前後幾天只有個位數到二十出頭）。判斷是來源在日期不精確時填當月 1 號，不是同步程式的錯。資料照存，但做時間序列或「哪天暴增」這類呈現時必須排除。驗收同步不能只看有沒有跑完、有沒有報錯，還要看資料的分布形狀——這種偏態不會觸發任何錯誤。

### 2.6 晚到的資料：排程時間不是防線（[#54][pr54]）

2026-10-04 第一次以一次性模式（同步跑完一輪就結束，§4.1）對雲端資料庫跑完一輪，機制全部正常，卻發現前一天（10/03，週六）所有市場都是「無資料，跳過」，同步進度照樣往前推；家禽最新只到 10/01，進度一樣推到 10/03。直接問農業部 API 才確認不是休市：歷史記錄裡每次「隔天去抓週六」都是 0 筆，同一批日期事後再問，台北一市場每天各有 300–348 筆。家禽則大約隔一天白天才公布。

成因是三件單獨看都合理的事疊在一起：同步進度「沒有錯誤就推進」、寫入只新增、推進之後不回頭。

| 選項 | 做法 | 結果 |
|---|---|---|
| **A. 回頭重掃（採用）** | 每一輪從「進度的隔天」與「昨天往前 6 天」取較早者開始抓 | 晚公布的日子下一輪自動補上；寫入時本來就濾掉已存在的資料，重抓不會重複 |
| B. 不改程式 | 文件寫明，需要時手動退進度 | 每天照樣抓空，首頁的雞蛋價格停在舊日期 |
| C. 排程改到晚上 | — | 家禽可能抓得到，週末行情仍缺，也補不回已經缺的 |

**修好機制不等於修好資料**：回頭重掃只保護改版之後的日子。拿本機資料庫逐日對農業部 API，2026 年 4–9 月農產品行情有 17 天整天沒有資料、家禽缺 4 天；退回進度補跑一輪，補回行情 84,449 筆、家禽 68 筆。其中整天缺的 17 天只佔 46,170 筆，**另外約 38,000 筆來自「只缺部分市場」的日子**——用「這一天有沒有資料」量不出來。完整度要量到資料的自然單位：日 × 市場（[`76e8d2f`][c-76e8d2f]）。

### 2.7 上游自己重複：全新的資料庫才會出現的失敗（[#58][pr58]）

容器化之後第一次在全新的資料庫驗收，休市日同步一開始就撞上唯一索引，整批一筆都沒寫進去。直接抓上游：21 個市場、32,171 筆日期裡有 10 組重複——同一市場、同一月份給了兩個版本的休市日。

同步程式只拿「資料庫裡已經有的」去過濾，沒有排除同一批資料裡的重複。舊的資料庫裡那些日期早就存在、會被濾掉，所以跑了幾個月都沒出事；全新的資料庫第一次同步就失敗，之後每次重試都一樣。修法是先排除同一批裡的重複、兩個版本取聯集，寫入 32,161 筆（[`8772ebd`][c-8772ebd]）。

「過濾已存在的資料」與「排除同一批裡的重複」是兩件事。寫入邏輯要在「有資料」與「全新」兩種資料庫各跑一次；全新環境的驗收，價值之一就是把這類被既有資料遮住的路徑翻出來。

## 3 架構取捨

### 3.1 跨模組只用邏輯外鍵，以及一條被「搆得到什麼」決定的外鍵（[#50][pr50]）

身分驗證的使用者資料表在 `ApplicationDbContext`，各模組的資料表在各自的 DbContext。EF Core 不會替跨 DbContext 的關聯建外鍵，所以各模組存使用者 ID 的欄位都是邏輯外鍵：欄位必填、資料庫層沒有約束，由程式負責一致性。

例外只有一條，而它出了問題。監看清單的使用者欄位有一條實體外鍵，指向「農場設定」資料表，而不是使用者資料表——結果沒填過農場設定的帳號，一新增監看就違反外鍵、拿到 500。回頭翻當初的 PR 與開發紀錄，兩份都詳細記了「這個 entity 沒有導覽屬性，所以關聯要改用泛型寫法」，卻一句也沒寫「為什麼主表選它」。再往下查才看清：使用者資料表在另一個 DbContext，同一個 DbContext 裡唯一以使用者為鍵的表就是農場設定，於是它成了主表。**主表是被「搆得到什麼」決定的，不是被「資料是什麼意思」決定的。** W26 拿掉這條外鍵，改成跟其他表一致的邏輯外鍵。

從這件事得到的判斷訊號：紀錄裡只寫了「怎麼寫」、沒寫「為什麼選」，通常代表當時根本沒有在選，那個設計可以改；寫了「考慮過 A 與 B、選 B 是因為……」的，要先確認 A 的問題還在不在。這也是這份文件把「被否決的選項」寫出來的原因。

### 3.2 共用抽象什麼時候抽

「兩段程式碼長得像」不是抽共用的理由。這個專案抽過幾次共用，每次的依據都不一樣：

| 抽出來的東西 | 依據 |
|---|---|
| 分頁抓取 `MoaPagedFetcher`（[#10][pr10]） | 相似來自**協定同源**：農業部所有分頁 API 都用同一套回應包裝，不會因業務不同而分岔；而且第三個使用者已經可以預見 |
| 排程外殼 `ScheduledSyncWorkerBase`（[#11][pr11]） | 不必預測：**13 支同步程式已經逐字重複同一段外殼** |
| 家禽四支來源的同步流程（[#30][pr30]） | **共用機械邏輯、不共用本質知識**：「按年切塊、推進進度、寫入」四支等價且最容易寫出差一錯誤，抽成一個方法；「怎麼抓、怎麼攤平」四支本質不同，各自獨立，以委派傳入 |

更早一次的判斷是反過來的：兩支氣象同步程式有七成結構相同，但要用大量泛型與委派才容得下兩者的差異，抽出來比原本更難讀，所以沒有抽——重複是該考慮抽象的訊號，不是命令。

抽出來之後也可能失效。一個入口頁的版面元件抽出來了，規格寫著四個模組都要用，實際上只有首頁在用、四個入口頁一個都沒做（[#52][pr52]）。兩輪全專案 code review 都沒查到，因為它們查的是「還有幾處舊寫法沒換過來」，可以 grep；**「當初說要用它的地方，有幾處真的在用」是另一個方向，程式碼裡沒有任何訊號**，只能拿規格回頭逐項對照。

### 3.3 只有一支端點用快取：判準是三條同時成立

全專案的快取（Cache-Aside：先查快取，查不到才查資料庫並寫回快取）只用在行情查詢一支端點。判準在模組入口頁那一輪寫下（[#52][pr52]），三條要同時成立才加：

1. **回應跟「誰在看」無關。** 回應會因呼叫者不同而不同時，整包快取會把甲的內容給乙。正確做法是拆兩層：與身分無關的部分走快取、與身分有關的欄位每次即時算；把使用者 ID 放進快取鍵是錯的，重複利用率會趨近於零。
2. **同一組查詢條件會被重複命中。** 行情查詢的條件是「作物＋市場＋日期區間」這種高度重複的組合；追溯碼查詢每次都是不同的字串，快取只會是淨成本。
3. **資料更新頻率遠低於查詢頻率，而且可以接受一段時間的陳舊。** 行情一天同步一次，快取 25 小時過期，最壞情況是看到昨天的數字，在行情的語意下可以接受。

另有一條否決條件：正確性依賴「寫入後立刻讀得到」的端點不用快取，因為快取失效的事件機制只是骨架，實際兜底的是過期時間（§8）。

## 4 部署上線：在免費額度裡活下來（[#54][pr54]）

### 4.1 額度的算術決定了同步程式的形狀

資料庫用的是 Azure SQL 免費方案：每月 100,000 vCore 秒（計費單位：用了幾個虛擬 CPU 核心 × 幾秒），用完就暫停到下個月。規格表上的計費下限是 0.5 vCore，換算可以醒 55.6 小時；實測醒著但沒有查詢時，每分鐘也計費 30.7–41 vCore 秒（記憶體用量把計費墊高到下限之上），實際約 40–54 小時。

同步程式原本是常駐的：同步一輪、睡到下一輪。常駐會讓資料庫一直醒著，一個月是 0.5 × 86,400 秒 × 30 天＝1,296,000 vCore 秒，約是額度的 13 倍。這不是偏好，是算術。改成**一次性模式**：GitHub Actions 每天觸發一次，17 支排程程式各跑完一輪，程序就自己結束。

- **完成的訊號是「試過一次」，不是「成功一次」。** 做成「成功一次」的話，一支連不上外部 API 的程式會讓整趟工作永遠等下去。結局分三種：逾時或全部失敗 → 結束碼 1；部分失敗 → 0 但記警告（外部資料源偶爾不通是常態，隔天會再跑）；全部成功 → 0。
- **改變執行頻率，會讓「一輩子只發生一次」的路徑變成主要路徑。** 迴圈末端「睡到下一輪」的等待原本在 try 之外，停機時的取消例外會直接跳出。常駐時一個行程只停機一次，沒人看出來；一次性模式每一輪都會走到那裡。

上線一週後實測（2026-10-13～10-20 共 8 輪；量法是 Azure Monitor 的 `app_cpu_billed` 逐分鐘加總，對照 Actions 每一輪的起訖時間）：每輪 810.6–894.1、平均 861.8 vCore 秒，以 31 天計一個月約 26,700，是額度的 27%。Actions 那一輪只跑 4.5–7 分鐘，資料庫卻醒了 21–23 分鐘——其餘是閒置等自動暫停；10-12 手動補跑、往回重抓 7 天的那一輪也只用 926.7。**成本由「醒著多久」決定，不由同步多少資料決定。**

### 4.2 「不拋例外」不等於「降級」（[`d35a291`][c-d35a291]、[`94ec53f`][c-94ec53f]）

部署形態只放得下資料庫、後端、前端三個服務，Redis 與 RabbitMQ 必須能不部署。原規劃以為它們本來就可以不部署，開工當天的本機實證推翻了這點：兩者都是硬相依（§7.6）。

改成可選相依：沒設 Redis 就改用行程內快取（存在後端自己的記憶體裡；`AddDistributedMemoryCache`，同一個介面的另一個正式實作，快取那段程式碼一行都不用改）；沒設 RabbitMQ 就不註冊事件消費者；快取讀寫的任何失敗都當成沒命中、回資料庫查。

做完再實測，Redis 指向不存在的主機時，行情查詢從 500 變成 200——但要 **12.45 秒**。Redis 用戶端斷線時會把指令排進佇列等重連，這支端點讀一次、寫一次，各等一輪逾時。**12 秒的 200 跟壞掉沒有差別。** 改成快速失敗（連不上就立刻回報失敗、不排隊等重連）之後：

| 情境（本機，同一支端點） | 結果 |
|---|---|
| 修改前，Redis 連不上 | 500，6.56 秒 |
| 只包 try/catch，Redis 連不上 | 200，12.45 秒 |
| 加上快速失敗，Redis 連不上 | 200，1.45 秒（第一次）／0.03 秒 |
| 完全不設 Redis 與 RabbitMQ（部署形態） | 200，1.67 秒（第一次）／0.034 秒 |

這幾個連線選項被改回預設時，不會有任何測試變紅、也不會有例外，症狀只有「慢」，所以另外寫測試釘住。降級的驗收標準是「失敗時多快拿到可用的結果」，不是「有沒有拋例外」。

### 4.3 資料庫睡著時的兩種失敗形狀（[`1b24d24`][c-1b24d24]）

資料庫平常是暫停的（閒置約 16 分鐘後暫停，恢復要 30–60 秒），同一條路徑上查到兩種失敗：

- **啟動時：錯誤 40613（資料庫暫時無法使用）。** 2026-10-01 第一次在資料庫暫停時啟動後端：寫入角色等初始資料（種子資料）那一步失敗 → 程式結束 → 平台重開 → 再失敗一次 → 平台封鎖 1 分鐘 → 第三次成功，但免費層的配額已被打爆，網站被停到整點，約 14 分鐘後才能用。12 處資料庫註冊全部改成遇到暫時性錯誤自動重試（最多 6 次、最長 30 秒）之後，10-02 重測 99 秒就能用，當天 4 次在資料庫暫停時啟動都是同一個形狀。
- **網站開著時：連線逾時 -2。** 2026-10-02 網站整天開著，資料庫每次自己暫停之後，第一個查資料庫的請求都會失敗，當天共 4 次。錯誤碼 -2 不在暫時性錯誤清單裡，不會重試，直接 500。

同一件事（資料庫正在恢復）因為時間差呈現成不同的錯誤碼：恢復快過連線逾時，拿到的是 40613（會重試）；慢過逾時，拿到的是 -2（不重試）。把 -2 加進重試清單被否決——-2 也代表「查詢跑太久」，加進去會讓慢查詢整個重跑最多 6 次。真正的問題是「連線等得不夠久」，所以改的是連線逾時（30 → 90 秒，依恢復時間的實測樣本 30／60／60／60 秒），前端每個請求的等待上限跟著拉到 120 秒，等超過 8 秒就分別問兩支健康檢查，畫面說明卡在「伺服器喚醒中」「正在喚醒資料庫」還是「仍在查詢中」。重測同一個情境，首頁的請求 52.7–57.9 秒全部 200。

### 4.4 一次性模式下會說謊的訊號

一次性模式的價值在於「跑完有一個可以相信的結論」。部署過程中查到幾個讓結論不可信的地方，形態都是「訊號跟事實不一致」：

- **空字串讓雲端每天多一則假失敗。** workflow 刻意把 RabbitMQ 主機名設成空字串（雲端沒有 RabbitMQ），程式卻寫 `設定值 ?? "localhost"`——`??` 只接得住 null，接不住空字串，同步成功後的事件發布必定失敗，被記成同步失敗。資料不會少，但每天一則假失敗會把真的失敗淹沒。更繞的是：空字串傳給 RabbitMQ 用戶端不會報錯，而是被當成 localhost，開發機上 RabbitMQ 正開著——不合法的值剛好等價於開發機上正確的值，這個 bug 在開發機上永遠是隱形的。
- **workflow 寫的值不是程式拿到的值。** `dotnet run` 預設套用 launch profile（本機開發用的啟動設定檔），profile 裡的 `DOTNET_ENVIRONMENT=Development` 蓋過了 workflow 設的 Production。指令加 `--no-launch-profile` 才生效。
- **「摘要說全部成功」只證明沒有例外。** 摘要只計丟出例外的同步，而多支同步程式遇到上游異常是記警告後停下、不丟例外。驗收改成直接看資料庫裡的同步進度與每天的筆數。

### 4.5 量具不能改變被量的對象

部署的每一個驗證步驟都在量雲端的狀態，有幾次量的動作本身改變了被量的東西：

- 要確認「程式醒著、資料庫睡著」，原本打算打一次網站看看——但打一次就把程式叫醒，冷啟動寫種子資料時還會順便叫醒資料庫。改看平台的管理面指標（請求數、記憶體用量），不碰程式本身。
- 登入後的通知鈴鐺每 60 秒查一次未讀數，分頁開著又登入時資料庫永遠不會自己暫停。驗證步驟補上「做完登出或關分頁」。
- 背景每 30 秒問一次 GitHub API 等排程跑完，半小時後撞到未登入每小時 60 次的上限；之後回的是錯誤訊息，監看腳本卻把「沒有那個欄位」當成「還沒開始」，排程跑完了也沒發現。量具拿不到答案時，要回報「量不到」，不能回報一個合法的狀態值。

## 5 容器化：一條指令起整站（[#58][pr58]）

部署上線之後，本機要把整站跑起來仍要裝 .NET SDK 與 Node.js、手動跑七次建表、另開視窗起前端。容器化要做到 clone 之後一條 `docker compose --profile app up -d --build`，同時保留 Visual Studio 的中斷點除錯流程不變。

### 5.1 兩種模式

不帶參數的 `docker compose up -d` 只起 SQL Server、Redis、RabbitMQ，後端在 Visual Studio 裡跑、可以下中斷點；加 `--profile app` 才再起建表、後端、同步程式與前端。被否決的是「預設就起整站」：對 clone 的人最直覺，但開發時打錯一次指令，就是容器裡的同步程式和 Visual Studio 裡的同步程式同時抓同一批資料。

### 5.2 建表用獨立的容器，而它借用了應用程式的啟動流程

| 選項 | 結果 |
|---|---|
| 後端啟動時自己建表（`Database.Migrate()`） | 要改應用程式碼；多個執行個體同時啟動會搶著建表，官方不建議正式環境這樣做 |
| **獨立的建表容器（採用）** | 七個 DbContext 的 migration 各打包成一支可執行檔，依序套用後結束；後端等它成功結束才啟動，應用程式碼不改 |

打包第一支就失敗：「Connection string 'DefaultConnection' not found」。EF 的設計階段工具要建出 DbContext 才能打包，沒有專用工廠時，它的做法是執行應用程式的 `Program.Main`、跑到建好 DI 容器為止——而後端在註冊服務時就檢查連線字串與 JWT 設定、缺了就中止（§7.3 刻意提前的那道檢查）。解法是打包階段給佔位值：打包不連資料庫，那個階段也不進最終映像。**借用應用程式啟動流程的工具（EF 設計階段工具、整合測試框架、Swagger 產生器）會繼承啟動流程的所有前提。** 代價也留著：七支各自帶著後端的完整相依，建表映像約 774 MB。

### 5.3 「共用同一個建置階段」不等於「共用編譯結果」

後端三個映像共用一份 Dockerfile、用 target 選擇，理由寫的是「方案只編譯一次」。重審時看 build log，編譯出現了三次：`FROM build AS x` 繼承的是 build 階段**已經做完**的東西，而共用階段只做了套件還原，下游各自的發布指令又各編一次。共用階段加一步編譯、下游一律 `--no-build` 之後（全新建置、無快取）：

| 項目 | 改正前 | 改正後 |
|---|---|---|
| 共用編譯 | 無（各自編） | 18.6 秒，build log 只出現一次 |
| 後端發布 | 74 秒 | 7.4 秒 |
| 同步程式發布 | 18 秒 | 3.8 秒 |
| 第一支建表程式 | 47 秒 | 29 秒 |

這句宣稱錯得不明顯：映像建得起來、功能全對，唯一的症狀是慢。而它正是選這個做法的依據，所以修法是改程式讓宣稱成立，不是改宣稱。

### 5.4 SQL Server 收不到停止訊號

`docker compose down` 時 SQL Server 沒有正常關閉，而是等逾時後被強制終止（結束碼 137），每次重啟都要靠交易記錄做復原。訊號送到的是容器裡的第一號程序（PID 1），而官方映像的第一號程序是一支 bash 啟動腳本：它把 SQL Server 放到背景，自己沒有處理 SIGTERM，也不轉送；Linux 對第一號程序沒有處理的訊號一律忽略。

| 做法 | 結果 |
|---|---|
| 只把等待時間拉到 60 秒 | 等滿 60 秒，照樣被強制終止 |
| 只加 `init: true`（由 Docker 內建的 init 當第一號程序） | init 把訊號轉給 bash，bash 自己結束，SQL Server 跟著被殺，記錄裡沒有關閉訊息 |
| **`init: true` ＋ 直接啟動 `sqlservr` ＋ 60 秒（採用）** | **2 秒、結束碼 0**，記錄「SQL Server is terminating in response to a 'stop' request」 |

判斷訊號有沒有送到，看關閉花了多久：遠短於寬限時間是自己關的，剛好等滿是被強制終止。

### 5.5 機密不進映像，判準不只是密碼

`.gitignore` 管的是「進不進 repo」，`docker build` 看到的是**工作目錄**——放了連線字串與金鑰的本機設定檔，一句 `COPY . .` 就會烤進映像。所以 `.dockerignore` 要再擋一次。前端的 `.env.production` 裡沒有任何密碼，只有雲端後端的網址，但它被帶進建置的話，容器裡的前端會去打雲端、而不是同一個 compose 裡的後端。要排除的是「換一台機器就該不一樣」的設定，不只是密碼。

## 6 測試與自動化檢查

### 6.1 挑「錯了不會有訊號」的地方測（[#46][pr46]、[#48][pr48]）

測試數量不是目標。選測試的判準是：**這段程式寫錯的時候，有沒有任何其他東西會發出訊號？** 沒有的地方才需要測試守著。

- **分頁的倍數邊界。**「還有沒有下一頁」由後端多撈一筆判斷。新舊做法只在「總筆數恰為每頁筆數的倍數」時給出不同答案，其餘情境測了也證明不了改動的價值。另補一條「要第 2 頁」：第 1 頁的跳過筆數算出來是 0，只測第 1 頁的測試分不出「有跳過」和「沒跳過」。
- **越權要測「存在但屬於別人」。**「標記已讀」的查詢條件是「ID 相符且使用者相符」。測「通知不存在」的測試在使用者條件被拿掉後仍然是綠的；只有「通知存在但屬於別人」那條會紅。而且要同時斷言「該筆仍然未讀」——例外只證明方法最後拒絕了，不證明它中途沒有寫入。
- **對外必須不可區分。** 登入時「帳號不存在」與「密碼錯誤」若回不同的錯誤，等於提供一支帳號列舉介面。兩種情境共用同一組斷言。連續失敗鎖定設成關閉時所有功能測試照樣通過，只能另外釘一條。
- **每一種「跳過」都是靜默的。** 規則引擎遇到設定不完整的規則會跳過、不拋例外，使用者看不到任何訊號，所以每個跳過分支各釘一條。

### 6.2 驗收測試：把實作真的改壞（[#46][pr46]）

寫完不只自問「改掉哪一行會讓這條測試變紅」，而是真的改壞六次、每次只改一處、跑完全部測試再還原：

| 改壞的地方 | 預期變紅 | 實際 |
|---|---|---|
| 「還有下一頁」的 `>` 改成 `>=` | 兩條倍數邊界測試 | 相同 |
| 多撈一筆改回不多撈 | 只有「多出一筆」那條 | 相同 |
| 刪掉跳過筆數那一行 | 只有第 2 頁那條 | 相同 |
| 規則名稱不從關聯資料取 | 只有規則名稱那條 | 相同 |
| 標記已讀拿掉使用者條件 | 只有越權那條 | 相同 |
| 零筆時的提早返回失效 | 只有零筆那條 | 相同 |

比「哪條紅了」更有價值的是「哪條沒紅、為什麼沒紅」——它證明每條測試各自不可取代。反過來，答不出「改哪一行會讓它變紅」的測試，只驗證了「程式沒有拋例外」，就不寫。同樣的方法在另一輪確認了測站查詢的第三段記憶體分組是唯一擋住跨測站錯誤配對的地方：拿掉它，八條測試中只有對應的那一條變紅（[#48][pr48]）。

### 6.3 斷言要分辨「走對了路」與「什麼都沒發生」（[#54][pr54]）

一則「外部要求停止時不能被記成逾時」的測試，本機連跑多次都過，在 CI 上偶發失敗一次。看起來像典型的 flaky test，調高逾時就好。先看失敗的狀態：被測的背景服務是「已取消」，而它被取消時是正常返回、不會拋例外——唯一的解釋是它根本沒有執行。最小實驗（啟動後立刻停止，兩萬次）裡 19,877 次背景服務的主程式沒有執行：.NET 10 用帶停機權杖（`CancellationToken`）的方式排程它，排程還沒輪到就被取消。

更要緊的是原本的斷言（結束碼 0、沒有呼叫停止）**在程式根本沒執行時也成立**，本機的綠燈有一部分什麼都沒驗到。修法是等被測對象記下「開始等待」才停機，並多斷言記錄裡真的出現「外部要求停止」。只斷言「沒有發生壞事」的測試，要再加一個「確實發生了該發生的事」的正向證據。

### 6.4 自動化檢查不得說謊（[#22][pr22]、[#43][pr43]、[#48][pr48]）

- **lint 的 `--fix` 讓 CI 顯示綠燈。** CI 跑的 lint 底層帶 `--fix`。第一次檢查時的結論是「不會掩蓋問題」：那批錯誤的規則沒有自動修正，只會回報（[#22][pr22]）。下一輪 code review 查到另一半：**有自動修正的格式類違規會在 CI 裡被修掉、結束碼 0、修正不會 commit**——違規留在 repo，CI 顯示綠燈。CI 改跑唯讀的檢查，修改模式只給本機用（[#43][pr43]）。
- **新檢查上線前，先對現況跑一次。**「未定義 CSS 變數」掃描初版回報 9 個命中，逐筆查證全部是假陽性，修正配方後才掛進 CI（[#43][pr43]）；擋 `toISOString()` 取日期的 lint 規則，上線前對還沒改的 13 處跑一次，恰好全部命中、沒有誤報（[#54][pr54]）。假綠燈讓人停止自己看；假紅燈訓練出「紅了先忽略」的習慣——兩者都等於廢掉檢查。
- **「記得掛屬性」不是機制。** 行情查詢的限流屬性掛在控制器類別上，新增端點自動涵蓋；漏掛的端點在測試、記錄與回應裡都跟有掛的一模一樣，所以另加一條反射測試（用程式讀出類別上掛了哪些屬性）釘住「這個類別上必須有限流屬性」（[#48][pr48]）。

### 6.5 CI 什麼時候接

CI 在 W20 才建（[#1][pr1]），不是一開始就有。W19 的測試 Sprint 先把單元測試補到 12 個，刻意用記憶體資料庫與模擬物件取代真實的 SQL Server 與 Redis，讓 CI 不需要任何外部服務就能跑；在那之前沒有基準線，CI 亮綠燈只代表「編譯得過」。到 2026-10-20，CI 有三個 job（測試數見 §1.2）：後端、前端、容器映像建置（建置四個映像但不推送——沒有自動化跑過的 Dockerfile，壞了也不會有人發現）。

## 7 被推翻的判斷

下面幾則都是當時有理由、事後證明不成立的判斷。原本的紀錄都保留著，只在後面補上更正。

### 7.1 「參數型別讓索引失效」——其實是篩錯了欄位（[`1409e34`][c-1409e34] → [`d160b07`][c-d160b07]）

- **當時**（2026-05）：作物選單的查詢逾時。看到 EF 送出的字串參數是 `nvarchar(4000)`，判斷是「參數與欄位型別不符，讓索引失效」，改寫成兩段式查詢繞過，還在程式碼留了診斷說明。
- **發現**（2026-06，code review）：蔬菜的選單裡出現花卉。直接查資料庫才看到市場代號是跨類別共用的——代號 400 同時是台中的蔬菜市場與花卉市場，用市場代號篩類別必然混進別的類別。真正代表類別的是 `TcType` 欄位，而它沒有索引，水果的查詢因此全表掃描、30 秒逾時。「選單被汙染」與「逾時」是同一個根因。
- **改了什麼**：改用 `TcType` 篩選並補上索引。2026-09 回頭查證，原本的機制本身也不成立：兩邊同為 `nvarchar`、只差宣告長度，SQL Server 不會因此放棄索引（會的是 `varchar` 欄位配 `nvarchar` 參數）。
- **教訓**：診斷停在第一個看起來合理的解釋。

### 7.2 強制推進的安全閥，13 天後拿掉（[`5a54aaa`][c-5a54aaa] → [`88a4be3`][c-88a4be3]）

- **當時**（2026-05-19）：行情同步有市場失敗時，進度不往前推。為了防止農業部 API 長期故障讓同步永久卡住，加了安全閥：落後 5 天仍有失敗，就強制推進並記警告。
- **發現**：強制推進會把「上游持續失敗」藏起來，而且留下補不回來的缺口。
- **改了什麼**（2026-06-01）：拿掉安全閥。有市場失敗就停在這一天、記警告、等人處理。**卡住本身就是訊號**，要做的是讓它被看見，而不是讓它自己過去。

### 7.3 「啟動時檢查」寫在 Scoped 服務的建構子裡（[#54][pr54]、[`82365b2`][c-82365b2]）

- **當時**：JWT 的三個設定缺任一個，在 `AuthService` 的建構子裡就拋例外，註解寫「Fail-Fast：啟動時就檢查」，測試也是綠的。
- **發現**（2026-09-26，部署前）：逐一清點後端讀的每個設定鍵、問「雲端從哪裡拿到這個值」，查到三個 JWT 設定在雲端沒有任何來源。而 `AuthService` 是 Scoped 服務（每個請求各建一份），要到第一個登入或註冊請求才會被建立——照原寫法部署，會是啟動成功、健康檢查全綠，第一個註冊的使用者拿到 500。測試測的是 `new AuthService(...)`：測的對象對，「啟動時」這個時機只存在於註解裡。
- **改了什麼**：檢查移到服務註冊階段，缺的鍵一次全部列出；另外擋下金鑰太短、有效天數不是正整數這兩種「啟動全綠、登入後才壞」的值。用建好的程式在正式環境設定、只給金鑰啟動，確認它在碰資料庫之前就結束。在第一次上傳後端之前修好，雲端沒有發生過這個 500。

### 7.4 `Task.WhenAny` 不會因為取消而拋例外（[#54][pr54]、[`2b5e35a`][c-2b5e35a]）

- **當時**：一次性模式的協調器用 `await Task.WhenAny(全部完成, Task.Delay(上限, 停機權杖))` 等待，再用 `catch (OperationCanceledException)` 接住外部停機。
- **發現**：2026-10-07 本機回補時手動按了 Ctrl+C，記錄卻寫「等了 180 分鐘仍未跑完」，結束碼 1——實際才跑 23 分鐘。`WhenAny` 回傳「最先結束的那個 Task」，而被取消也算結束；它自己的 Task 是正常完成的，`await` 不會拋任何例外，所以 `catch` 永遠進不去，外部停機一律被判成逾時。
- **改了什麼**：`WhenAny` 回來之後看停機權杖，記下「外部要求停止」與還沒跑完的名單。既有四則測試涵蓋的都是協調器自己判斷的結局，「外部要求停止」是第五種，補上的測試先在舊程式上確認是紅的。

### 7.5 測試對了，理由寫錯了一個月（[#54][pr54]）

- **當時**：健康檢查分兩支：`/health` 不碰資料庫，`/health/ready` 才檢查資料庫。有一則測試釘住「資料庫檢查要帶 ready 標籤」，註解寫的理由是：標籤掉了，`/health` 就會每次去碰資料庫，把額度燒光。
- **發現**（開 PR 前逐行重審）：`/health` 的篩選條件從第一版起就是「一項都不跑」（[`4077774`][c-4077774]），跟標籤無關。標籤掉了，真正的後果在另一支：`/health/ready` 一項都不跑、永遠回 200，部署後的驗收與暖機從此碰不到資料庫，前端也會在資料庫還在醒的時候說「仍在查詢中」。
- **改了什麼**：改正註解與測試名稱。這個錯在測試註解、設計紀錄、PR 描述初稿三個地方存在了約一個月，三處彼此一致，交叉比對永遠抓不到。理由寫錯的代價比沒寫更大：讀的人會照著錯的理由判斷「這則測試可以刪嗎」。

### 7.6 「RabbitMQ 沒有流量，可以不部署」（[`d35a291`][c-d35a291]）

- **當時**：部署規劃假設 RabbitMQ 沒有實際流量，可以不部署；Redis 只是快取，應該可以降級。
- **發現**（2026-09-12，開工當天的本機實證）：RabbitMQ 主機名指向不存在的主機時，事件消費者在啟動階段拋例外，而背景服務啟動時拋例外的語意是「整個 host 起不來」——程式直接結束。Redis 連不上時，行情查詢先卡 6.56 秒再回 500。兩者都是硬相依。
- **改了什麼**：兩者改成可選相依（§4.2）。照原規劃部署要五個服務，少任何一個，使用者看到的不是「慢一點」而是「壞掉」。

### 7.7 部署方式的兩次對調（[#54][pr54]、[#58][pr58]）

- **先容器化再部署 → 先部署。** 原規劃先寫 Dockerfile 再部署。2026-09-08 對調：Dockerfile 怎麼寫取決於部署到哪個平台，而 Azure App Service 可以直接吃 .NET 發布包、不需要容器；先寫可能寫出一個選定平台用不到的版本。容器的真正價值是本機一鍵起整站，跟部署不是同一件事，所以排在部署之後（§5）。
- **自封裝發布 → 框架相依。** 原本選自封裝（把 .NET 執行環境一起打包），理由是查不到 App Service 支援 .NET 10 正式版的一手說法。2026-09-24 建立 App Service 時，下拉選單已顯示「.NET 10 (LTS)」——選擇的前提不成立了，就回頭重審：改走框架相依，平台自己找得到程式、不需要啟動命令，上傳的 zip 13.5 MB。
- **教訓**：理由是「某件事還不確定」的選擇，那件事一確定，就要回頭重審那個選擇。

## 8 沒做的事與理由

[README 的「已知限制」](../README.md)逐條列了沒做的項目與理由，包括免費方案本身的上限。這裡挑幾則「考慮過、決定不做」的：

- **訊息佇列沒有可靠投遞。** 事件消費者用的是臨時佇列（消費者斷線就跟著消失），也沒有死信佇列（存放處理失敗的訊息、事後可查）。不補的理由是它沒有承載任何實際工作：收到事件只記一行記錄，行情快取靠 25 小時過期兜底，雲端也不部署 RabbitMQ。要讓它承載流量時，持久佇列、死信佇列與快取失效要同一次做。
- **呼叫農業部 API 的重試不涵蓋逾時。** 逾時的結果是那一輪同步失敗、進度不推進、下一輪從同一天重抓——資料不會漏，只會晚一輪。把逾時也納入重試，要先決定「單次逾時」與「整體時間預算」怎麼分，那是另一件需要設計的事。
- **往回重抓只看 7 天。** 公布延遲超過 7 天（例如春節長假）的日子會缺。多看一天，行情同步每天就多打 25 次 API；遇到長假後手動把進度往回改再跑一輪即可。
- **通知規則不開放「樹木病蟲害」與「病蟲害旬報」當來源。** 前者沒有時間戳與唯一識別欄位，無法判斷「新出現」；後者要比對的數值欄位上游全部是 null，任何門檻都不可能成立。兩者都不是補欄位救得回來的。
- **規則的縣市沒有後端白名單。** 後端再寫一份 22 個縣市的清單會變成第二份真相來源，而兩個資料源的縣市涵蓋範圍本來就不同。正確的做法是後端提供縣市清單端點，那要先解決涵蓋範圍不同的問題。
- **資料庫防火牆對 GitHub Actions 開放得偏寬。** 執行器的 IP 不固定，所以允許所有 Azure 服務存取。收窄要在 GitHub 那邊再保管一組 Azure 認證——用一組更敏感的憑證換一個較窄的網路範圍，在資料全是公開政府資料、寫入都要登入的前提下不划算。
- **分享連結的預覽（伺服器端渲染、Open Graph：分享到社群時顯示的標題與縮圖）。** 沒有人在分享連結，先不做（[#24][pr24]）。
